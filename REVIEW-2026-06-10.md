## 1. Risk & process (most important)

### 1.1 The Kelly doubling was the exact mistake the brief warns against
Timeline from the repo itself:

- Jun 4 (ROADMAP): bankroll ~$106.96, 5 bets logged, 3 settled
- Jun 9 (config comment): KELLY_FRACTION doubled 0.125 → 0.25 and MAX_BET_PCT doubled 3% → 6%, justified by "+15% ROI outside one outlier" on a sample "still building toward 50 bets"
- Today (settings.json): bankroll $61.26 — below the $75.04 start

Sizing was doubled on ~3 settled bets of evidence, mid-run, and the bankroll has since dropped ~43% from its peak. The brief's own words: "Assume I am fooling myself."

**Recommendation:** revert to 0.125 (or 0.10) and 3% cap, and write a pre-commitment rule into config: sizing may only change after ≥200 settled bets AND positive mean CLV. No mid-drawdown changes in either direction.

### 1.2 MIN_EDGE = 15% is a red flag, not a feature
MLB moneyline is one of the most efficient markets in sports. Genuine model edges are 1–5%. When your model disagrees with the vig-free market by 15+ points, the most likely explanation is that the market knows something the model doesn't (injury, lineup, weather, sharp money) — i.e., the filter selects for the model's *worst* mistakes, not its best picks. The threshold sweep finding ROI maximized at 15% on 168 bets is consistent with overfitting to a small sample where some big-disagreement bets happened to win.

**Recommendation:**
- Add `market_implied_prob` as a model feature (already ROADMAP item 5 — promote it to #1 priority). A model that sees the market and still finds a small residual edge is far more trustworthy than one that ignores it.
- Treat CLV, not backtest ROI, as the threshold-selection criterion.
- Re-run the sweep on **real-odds bets only** (the sweep already tracks `real_odds_bets` vs `synthetic_odds_bets` — filter the summary on it).

### 1.3 Thresholds tuned and evaluated on the same sample
MIN_EDGE, MIN_MARKET_PROB, and MAX_AMERICAN_ODDS were all chosen by sweeping the 2022–2025 walk-forward window, and the "+12.9% ROI" headline comes from that same window. That ROI is an in-sample-of-the-sweep number; expect substantially less live. Hold out 2025 (or 2026 paper results) entirely from threshold selection.

### 1.4 Correlated exposure across markets isn't capped
ML, F5, and props each size off the full bankroll independently in the same daily run. An ML bet and an F5 bet on the same game are strongly correlated (same starters), and a K-prop on a starter correlates with both. Worst case the same game thesis is bet three times at full Kelly each.

**Recommendation:** cap total daily exposure (e.g., 15% of bankroll) and either skip F5 when an ML bet exists on the same game or halve both stakes.

## 2. Real bug: train/live feature mismatch on one-sided missing data

In training (`features/engineering.py`), a diff where *either* side is missing becomes NaN and is filled with **0** ("no edge either way").

In live (`paper_trade/live_features.py`), missing values are coerced to 0 *before* subtraction:

```python
"sp_fip_diff": (home_sp.get("fip", 0) or 0) - (away_sp.get("fip", 0) or 0),
```

If the home SP has no prior-season stats but the away SP has FIP 3.80, live produces `sp_fip_diff = -3.80` — to the model, that reads as "home pitcher is elite by a margin that never occurs in training data." Same pattern affects `sp_k_pct_diff`, `sp_bb_pct_diff`, `sp_era_diff`, `woba_diff`, `team_era_diff`, `team_fip_diff`. `sp_data_available=0` flags it but does not neutralize the bogus diff.

This is plausibly a direct contributor to the inflated 15%+ "edges" on live picks (rookie/returning starters with no prior-season line are exactly the games where this fires).

**Fix:** in live feature construction, compute each diff only when both sides are present, else 0 — mirroring training exactly. Worth an assertion/unit test that live and training feature builders agree on synthetic inputs.

## 3. Settlement bugs

- **Integer-line pushes on props.** `settle_prop_bets` and `settle_batter_hit_bets` use `actual > line`; with an integer line (e.g., 6.0 Ks, actual 6) the bet should void, but it settles as an under win / over loss. Books do post integer lines. Add `actual == line → outcome -1, profit 0`.
- **Postponed ML games never resolve.** ROADMAP item 12 already notes it; `settle_bets` should auto-void bets older than ~36–48h whose game never went final (the batter-hits DNP auto-void shows the pattern).
- **K-prop settlement matches pitchers by normalized name** against `PitcherSeason`. Name collisions (e.g., Luis Castillo) can settle the wrong pitcher's line. The prop already stores `player_id` — populate and use it.

## 4. Modeling

- **Isotonic calibration is why probabilities floor at ~35%.** Isotonic can't extrapolate outside the training range, and MIN_MARKET_PROB=0.20 is a band-aid for it (config says as much). Try `method="sigmoid"` (Platt) for comparison, and/or the market-prob feature from 1.2, which fixes the root cause.
- **Strikeout model: park factor applied only at predict time.** The Ridge model never saw `PARK_K_FACTOR` in training, then live predictions get multiplied by it — double-counting anything park-correlated in the features, with a hand-typed 15-team table (the other 15 teams silently get 1.0). Either make it a training feature or drop it.
- **Poisson tail conversion is shaky for both props.** Strikeouts per start are bounded by pitch count (variance < mean); hits are bounded by ABs. Poisson will misprice the tails — and tails are exactly what over/under betting prices. Validate the *probability* calibration of prob_over (binned, walk-forward), not just MAE. A negative binomial or empirical residual distribution would be better.
- **K model has no walk-forward validation** — `train_k_model` prints in-sample MAE only (the hits model does it properly). Add the same `walk_forward_validate` before trusting K props, especially since ROADMAP calls K props the "highest-edge" market.
- **Backtest bets at closing odds.** Conservative in one sense (close = sharpest price), but it means backtest ROI is not measuring the thing paper trading measures (morning line + CLV). Fine — just don't compare the two numbers directly.

## 5. Smaller items

- `betting/kelly.py` docstrings are stale: says default eighth-Kelly 0.125 (now 0.25), "max_pct default 5%" (now 6%), "rounded to nearest dollar" (rounds to cents). Stale docs around risk parameters are how the next bad sizing decision happens.
- `daily_picks.py` docstring claims idempotency via "UniqueConstraint on game_pk + bet_side"; the actual constraint is game_pk only. The code checks before insert anyway, but fix the comment.
- Mixed odds basis in logging: `edge` is computed off the consensus book, the bet is logged at the *best* book's odds, and CLV compares best-book entry to consensus-pair close. Each choice is defensible but the analysis mixes bases; store both consensus and best-price edge so CLV analysis is apples-to-apples.
- ROADMAP bankroll figures are stale; settings.json is the source of truth. Consider a tiny `bet_log` audit table (timestamped bankroll snapshots) so you can reconstruct the equity curve exactly.
- **No tests.** `odds.py` was written pure "so they are easy to unit-test" — there are zero tests. Highest-value targets: vig removal round-trips, Kelly edge cases, push settlement, and the train/live feature parity check from section 2.
- F5 odds fetching costs 1 API request per event per day, which contradicts the "2 requests/day, free tier lasts ~8 months" plan in `odds_api.py`. Track quota burn.
- Hygiene: stray `.swp` in the folder root; `.env` holds the real key and is git-ignored (good) — worth a one-time `git log --all -- .env` to confirm it was never committed.
